# The live movement validator in the real engine: what broke versions 50/51 (2026-11-21)

Version 51 (enforcement on) put the owner back at the start after a few seconds and lagged; version 54 (enforcement off in `Server/Main`, log-only) runs fine by his word. Nobody could observe the live game (Luau Execution 403), so six read-only investigations read the code at `3bab8cd`, each from one angle, and a second reader tried to refute the stronger claims. None is measured in the engine. **Before enforcement is switched back on, every item marked likely or possible below needs a fix and a look in the real game (the owner's F8 panel shows the validator's flags by code in log-only mode).** Fixed already: the anti-gravity force sized from an anchored body (`BodyDriver`, in `554fe04`); warn floods bounded.

## Findings, most likely first

### [likely] The pin makes the client build its anti-gravity force on an ANCHORED root: AssemblyMass is infinite there, so the force is (0, inf, 0) and is let loose the moment the first packet un-pins the body

- **Where:** /home/user/spicy-rodents-roblox/src/client/Controllers/BodyDriver.luau:27-42 (antiGravity, line 36), 67-87 (driveRender); /home/user/spicy-rodents-roblox/src/client/Controllers/Squirrel.luau:342 (driveRender call), 360-372 (movedFromOutside restart); /home/user/spicy-rodents-roblox/src/server/Movement/BodyPin.luau:37-52 (pin), 58-74 (unpin); src/server/Movement/MovementService.luau @3bab8cd:664-670 (pin at hand-over), 787-806 (unpin), 1026 (watch skips a non-finite root), 1147 (drift), 620-631 (hold), 1033-1036 (held teleport); /home/user/spicy-rodents-roblox/src/server/Actors/Possession.luau:254-283 (possessNow order); /home/user/spicy-rodents-roblox/src/server/Actors/ActorService.luau:82-83
- **What happens:** 1. Version 47: possessNow sets the root un-anchored (ActorService setMode 'player': `root.Anchored = false`), hands it to the player, then fires Granted. The client's controller started on an UN-anchored root.
  2. Versions 50/51: in the same server step, Possession's onHandoff reaches MovementService.onHandoff, which (enforcement on, squirrel family) calls `engine.pin(id, true)` -> BodyPin.pin: `root:SetNetworkOwner(nil)`, `root.Anchored = true`. Granted is fired after that, so on the client the root is anchored when Controllers/Squirrel.start runs, and stays so until the first packet has gone up, passed the gate and the un-pin has come back down.
  3. Squirrel.start line 342 calls BodyDriver.driveRender(root, ...), whose first act is antiGravity(root): `anti.Force = Vector3.new(0, root.AssemblyMass * workspace.Gravity, 0)` (BodyDriver.luau:36), computed once, never refreshed. Roblox documents that an assembly containing an anchored part has infinite mass (AssemblyMass reads inf). The squirrel is one anchored root plus Motor6D limbs (HANDOFF rule 4), so the force is (0, inf, 0). I could not open create.roblox.com from this session; the statement comes from a web search of the official AssemblyMass / assemblies pages and matches the known behaviour.
  4. First packet passes the gate -> MovementService unpin -> BodyPin.unpin: `root.Anchored = false`, `root:SetNetworkOwner(driver)`. The client now simulates the root with an infinite upward VectorForce (the force is a client-local instance, so only the owner's physics has it).
  5. What the engine does with an infinite force is the part nobody has seen. Every plausible outcome breaks play, and each has a signature in the validator:
    a. The root's physics state goes non-finite between frames (the controller still writes a finite CFrame before each render, so the owner sees his squirrel and runs on). If the server never gets a usable root, its copy stays where the pin kept it. I ran this on the rig (root updates never arriving): 'drift' snaps at 2.07 s, 4.13 s and 6.20 s after the hand-over (the 2 s `prior` window, MovementService 802/1147), the third one a 2 s hold (620-631), then the 'held' teleport (1033-1036) puts the player back where the hold began, and the cycle repeats about every 4 s.
    b. The root comes back finite but thrown far: Squirrel.luau:361-372 takes it for a move the server made and restarts the motor there (`SquirrelMotor.place(state, at.X, soles, at.Z, ...)`); the next packet is 'malformed'/'teleport'/'gate', the snap restores the last clean packet, which stays the one right after the un-pin (the start), three snaps make a hold, during the hold the root is anchored again (no force), the player runs free for 2 s and is then put back at the hold place: runs a little, back to the start, again and again.
    c. The root reads +inf: the motor is placed at y = inf, every packet is dropped by Net as 'non-finite' (Net.luau:123-127), the watch returns early on a non-finite root (1026): the squirrel is gone for good.
  6. Version 54 (enforcement off) never pins, so the root is un-anchored at controller start and the mass is finite: the hotfix removes this by side effect, without the validator's judgements having been the problem.
- **Symptoms it explains:** Snap back after seconds: good for outcomes a and b (free running for a few seconds, then put back; b returns to the start itself, a to where the hold began). Lag: good (a snap hitch every 2 s, 2 s freezes, or a snap storm). Start screen / respawn: only indirectly (the server holds the body at the start, so anything that reads the held place acts there). It also fits the history exactly: fine in 47 (no pin), broken in 50/51 (pin), and it would be cured by 54 for a reason other than the one assumed.
- **Why the specs miss it:** BodyDriver is engine-only (Instance.new('VectorForce'), AssemblyMass) and never runs under Lune. tests/lib/LiveRig models the pin as a boolean (`server.pinned`) and the client's root as the motor's own point with no physics, so an anchored start, its mass and the hand-back of the physics do not exist there. Enforcement with the pin had never met a real client before versions 50/51.
- **Fix:** Never size the force from AssemblyMass on an anchored root. In BodyDriver.antiGravity take the mass from the parts (root:GetMass() plus every non-Massless part's GetMass(); the limbs are Massless, so root:GetMass() alone today), or refresh `anti.Force` each frame only while `root.AssemblyMass` is finite and the root is un-anchored (and on the root's Anchored changed signal). Guard the controller: a root position that is not finite must not restart the motor. Give the fake engine an AssemblyMass that is math.huge while anchored and add a spec that the force is finite when a controller starts on a pinned body. Do not turn enforcement back on from a clean log-only run alone: log-only never pins, so it cannot show this.
- **How to confirm in the game:** Studio command bar: `local p = Instance.new('Part'); p.Anchored = true; p.Parent = workspace; print(p.AssemblyMass)` prints inf. In a two-window Studio test of the 3bab8cd build, pick a squirrel and print on the client `root.Anchored` at Squirrel.start and `root.BodyDriverAntiGravity.Force`: (0, inf, 0). On the server print the held squirrel's `PrimaryPart.Position` and `movement:stats().reasons` every second: either the root stays at the hand-over place while packets are accepted and 'drift' rises every ~2 s with holds, or the position is nan/inf, or 'malformed'/'gate:*' climb. A second player would see the squirrel standing at the hand-over place or vanishing.

### [likely] The pin makes the client build its anti-gravity force from an anchored body: AssemblyMass is infinite there, so the force is infinite, and the squirrel's physics break as soon as the server hands the body back

- **Where:** src/client/Controllers/BodyDriver.luau:27-42 (line 36: anti.Force = Vector3.new(0, root.AssemblyMass * workspace.Gravity, 0)) and :66-70 (driveRender calls antiGravity once, at start); src/client/Controllers/Squirrel.luau:342 (driveRender at controller start), :360-372 (root read back each frame, movedFromOutside); src/client/Possession/PossessionClient.luau:361, :367-403 (controller started straight from Granted); src/server/Actors/Possession.luau:256-296 (unanchor + owner, then onHandoff, then Granted, all in one frame); src/server/Movement/MovementService.luau:664-670 (pin at hand-off, only when enforcing), :787-806 (unpin, prior window), :1024-1028 (watch returns on a non-finite root), :1081-1147 (drift, prior); src/server/Movement/BodyPin.luau:37-53, :58-74; src/server/Boot/Game.luau:1053-1083 (watch reads root.Position)
- **What happens:** 1. Version 47 and version 54 (log-only): Possession.possessNow unanchors the root and gives it to the player BEFORE Granted is fired (ActorService.luau:83, Possession.luau:256-257), so when the client starts Controllers/Squirrel the root is unanchored and BodyDriver.antiGravity reads a finite AssemblyMass.
  2. Version 50/51 (enforcement on): in the same server frame MovementService.onHandoff pins the body again (MovementService.luau:664-669 -> BodyPin.pin: SetNetworkOwner(nil), Anchored = true). The pin exists only when enforcing(), so the hotfix removed it. The replicated state the client sees when Granted arrives is Anchored = true (it was anchored as an AI body before, too).
  3. PossessionClient starts Squirrel.start at once (no wait for the pin's release); Squirrel.luau:342 calls BodyDriver.driveRender, which calls antiGravity(root) ONCE. Roblox documents that an assembly with an anchored part has infinite mass (create.roblox.com/docs/reference/engine/classes/BasePart/AssemblyMass: "If the assembly has an anchored part, the assembly's mass is considered infinite"; forum reports of AssemblyMass printing inf). So Force = (0, inf, 0), never recomputed.
  4. The first packet passes the gate, MovementService.unpin -> BodyPin.unpin sets Anchored = false and SetNetworkOwner(driver). About one round trip later the client simulates the body with an infinite upward VectorForce. Forum reports for non-finite forces: parts get NaN positions, flicker, or are deleted, and NaN spreads to everything the same client simulates (devforum threads 315268, 2927106, 2654376, 23361; I could not open them from this session, devforum.roblox.com is not an allowed host, only the search summaries).
  5. What the code then does, by engine variant:
    (a) the server's copy of the root stops following (non-finite updates not applied): the watch sees a root standing where the server last put it while packets move on. For the first 2 s that is excused (unpin sets sq.prior = the pinned place, priorUntil = now + max(2, 2*ping+1): MovementService.luau:799-803, 1140-1146), then `drift` fires. I ran this in the project's own LiveRig from a scratch script outside the repo (honest runner, root updates never taken): drift snap at 2.15 s, 4.15 s, 6.2 s, the third with a 2 s hold, then a snap + hold every ~4.15 s, each hold throwing the client back 2 s of running.
    (b) the server's root becomes NaN/inf: watch() returns at line 1026 (`not finite3`) and never judges the root again; server code reading root.Position (streaming focus, Net.fireNear, poseOf at release) works on NaN.
    (c) the client reads root.Position = +inf: Squirrel.luau:360-372 takes it as `moved by the server` and SquirrelMotor.place()s the motor at y = inf; every packet is then non-finite and Net.receive drops it (Net.luau:122-126), so the server never corrects it (see finding 3).
    (d) the engine deletes the non-finite parts: the body loses its PrimaryPart for the server's lifetime.
  6. The squirrel's drawn pose can still look right for a while in (a)/(b): the controller rewrites root.CFrame every render frame and NaN fails the `>` test in movedFromOutside, so the motor is not disturbed.
- **Symptoms it explains:** Fits all three facts that bound the fault: new with the pin (18 Nov, never played before version 50/51), gone in version 54 (no pin when enforcement is off), invisible to every headless check. Variant (a) reproduces the owner's words closely: nothing wrong for about 2 s, then rubber-band snaps ("lags"), then from about 6 s a hold every few seconds that puts him back where he was 2 s earlier ("gets some distance, then is back where he began"), and with finding 2 he is pinned to one place. Variants (c)/(d) would look like the squirrel vanishing rather than jumping back, so the match depends on which engine behaviour is real. Does not by itself explain a return to the play menu.
- **Why the specs miss it:** LiveRig has no physics and no anti-gravity: its root is the motor's own x, y, z copied to the server at 30 Hz (tests/lib/LiveRig.luau:396-417), and its pin only stops those copies. The isolated fakes set AssemblyMass = 1. The four place tests run the server with no client, so BodyDriver never runs against a pinned body.
- **Fix:** In BodyDriver never size the force from an anchored assembly: sum part:GetMass() over root:GetConnectedParts(true) (finite when anchored), or set the Force each frame from AssemblyMass only when it is finite (zero otherwise) so it also follows clothing/mass changes and holds; refuse a non-finite force outright. In Controllers/Squirrel ignore a non-finite root.Position instead of placing the motor there. Add an isolated spec with a fake root that is Anchored with AssemblyMass = math.huge at controller start. Keep enforcement off until this is in.
- **How to confirm in the game:** On the diagnostic panel, client side, at squirrel controller start print root.Anchored, root.AssemblyMass and BodyDriverAntiGravity.Force: with the pin on it should read true, inf, (0, inf, 0); with version 54 false, a small number, a finite force. Then print root.Position at the top of each frame: it turns nan/inf within a fraction of a second of the first packet. Server side print root.Position at each watch and MovementService:stats().reasons: expect a root that stops moving and `drift` every ~2 s, or a non-finite root with no snaps at all, or Net's log line `dropped Squirrel.State from <id>: non-finite`. In Studio alone: anchor a part and print its AssemblyMass (inf).

### [likely] The hold is a trap for an honest player who keeps pressing forward: he is never told he is held, runs on locally for 2 s, is thrown back, and is snapped `drift` and held again every 2 s without end

- **Where:** src/server/Movement/MovementService.luau:601-634 (tell: third snap in 10 s -> engine.hold), :1029-1037 (given back: teleported `held`), :1135-1147 (after the give-back the root is judged against the new gate with almost no reach; prior is still the place before the snap), :1434-1451 (packets dropped while held); src/server/Movement/BodyPin.luau:167-207 (hold: anchor + own; a separate task.delay hands it back); src/server/Boot/Game.luau:972-988; src/client/Controllers/Squirrel.luau:342-372 and src/client/Controllers/MotorLink.luau apply() (no held state: the motor keeps taking input; a `held` correction just places it back)
- **What happens:** 1. Any three counted snaps inside C.HOLD_WINDOW (10 s) make tell() call engine.hold: the server anchors the body for 2 s at the snap place h and sets sq.heldUntil.
  2. The client gets only the ordinary snap Correction. Nothing in Controllers/Squirrel or MotorLink knows about a hold, so the motor keeps running on the player's keys and writes root.CFrame locally on a body it no longer owns; its packets are dropped as stale (line 1434). On screen he runs normally for 2 s.
  3. After 2 s the watch calls teleported(h, `held`) (new epoch, Correction with snap = false -> MotorLink.apply places the motor back at h: the visible jump back), and BodyPin's own timer unanchors the body and gives it back. Two independent timers, usually the unanchor first (task.delay fires on the first frame after 2 s, the watch on its next 15 Hz tick).
  4. Root updates the client sent before it applied that correction still carry the run-away place. The watch has no packet yet in the new epoch, so it judges the root against the gate h with reach 8 + reachIn(v+55, ~0 s) (line 1135-1138); sq.prior is the last packet before the snap, also near h. A root 30-40 studs off is `drift` -> snap -> the 10 s window still holds three snaps -> held again.
  5. Verified with the project's LiveRig from a scratch script (not in the repo): three forced snaps at 1-3 s, then a plain honest runner holding forward, 40 ms each way: snaps 4..20 are all `drift`, 18 holds in 40 s, one every 2.05 s, the client's distance from the start oscillating between 48.8 (the hold place) and ~84 and never passing it. Same at 150 ms each way. It ends only when the keys are released for a couple of seconds (run with a pause at 9-12 s: free from then on).
  6. In the real engine the leak in step 4 needs the client to own the body for a frame or more before it applies the `held` correction, so each cycle repeats with a probability rather than always; that probability cannot be read from the code.
- **Symptoms it explains:** The shape is exactly "gets some distance, then is back where he began", every 2 s, for as long as he keeps trying to move, and feels like lag. "Where he began" is the hold place, which is the start if the three snaps come right after taking the squirrel. It needs a trigger of three snaps in 10 s: finding 1's drift snaps supply it, and so would any honest false positive of the packet validator in the real engine (other lenses).
- **Why the specs miss it:** Every rig case that reaches a hold is a cheat, where staying held is the wanted result (`held after a run of snaps`). No spec has an honest client in a hold, and honest rig runs never reach three snaps. The rig also lets root updates through the instant the hold ends, so it shows the loop readily; nobody asked it.
- **Fix:** Tell the client about a hold (the Correction carries the seconds; the controller feeds idle input and shows a short notice) and stop its motor for that time. Hand the body back and send the `held` move from one place in one order (correction first, then unanchor/owner; no separate task.delay). After a give-back do not judge the root against the gate until the new epoch's first packet has passed it (or for ignoredFor), and never count a snap in that window toward the next hold. Add a rig spec: three forced snaps, an honest runner who never lets go must be free after one hold.
- **How to confirm in the game:** Server log: `<id> held for 2 s after N snaps` repeating about every 2 s with reason drift each time, snaps climbing while the player only runs straight. On screen: about 2 s of running, thrown back to the same spot, again and again; standing still for 3 s ends it.

### [likely] Every put-back in possession lands on the validator's held place, which under enforcement is the hand-over spot until a packet is judged clean (why the destination is 'the start')

- **Where:** /home/user/spicy-rodents-roblox/src/server/Movement/MovementService.luau:902-963 (safeTarget, heldPlace, at 3bab8cd); /home/user/spicy-rodents-roblox/src/server/Actors/Possession.luau:190-215 (releaseNow teleports to heldPose) and :343-383 (recover); /home/user/spicy-rodents-roblox/src/server/Actors/ActorsRuntime.luau:302-316 (safePose), :435-456 (held squirrel fed from heldPlace, automatic recover), :516-520 (Reset remote)
- **What happens:** This is not a trigger by itself; it is the reason any trigger returns the player to where he began rather than a step back. heldPlace returns `sq.good` (the last CLEAN packet) and otherwise `sq.gate or sq.pinAt or sq.base`, the hand-over pose. The automatic recover itself can only fire when the HELD place is in the river at or below the water line, below the floor (y under (bedY - 6) units) or non-finite, and at most once per 3 s (Possession.RECOVER_EVERY), so it is not an ordinary trigger within seconds unless the hand-over spot is over water.
- **Symptoms it explains:** Snap back to where he began: explains the destination well, for any validator-side trigger. Lag / respawn / start screen: not explained by this.
- **Why the specs miss it:** In Lune the honest rig's packets are judged clean, so the held place tracks the body and every put-back lands next to it; the specs never run with a held place that has stopped advancing for an honest player.
- **Fix:** The hotfix's log-only heldPlace (newest packet) removes it. - **How to confirm in the game:** The diagnostic line should show the held place against the newest packet's place: under enforcement in the real engine the two drift apart (held stays at the hand-over spot, cleanAt never moves) while packets keep arriving. Pressing the Roblox menu's Reset in that state puts the body back at the hand-over spot.

### [likely] A hold never ends for a player who keeps moving: the client is not frozen during the server's 2 s hold, the give-back finds the root far from the held place, a 'drift' snap follows, and the uncleared snap count re-holds at once

- **Where:** As of 3bab8cd: src/server/Movement/MovementService.luau:601-632 (tell: snapTimes, hold at 3 in 10 s; snapTimes never cleared), :1029-1037 (watch: hold over -> teleported "held"), :1128-1147 (drift against the gate / prior), :1434 (packets dropped while held); src/server/Movement/BodyPin.luau:167-207 (hold: SetNetworkOwner(nil), Anchored, timer give-back); src/client/Controllers/Squirrel.luau:342-530 (frame loop: nothing stops the motor while the body is held); src/client/Controllers/MotorLink.luau:104-135; tests/lib/LiveRig.luau:329-337 and :400-415 (the rig's hold).
