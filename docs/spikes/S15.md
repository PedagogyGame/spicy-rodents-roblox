# S15 Developer products, ProcessReceipt and the DataStore profile

**Verdict: PARTIAL.** The receipt logic, the session lock and the DataStore path in Luau Execution
are **GO**. Three checks still need the owner: a real developer-product purchase in Studio, the
balance surviving a Studio stop and start, and an Open Cloud DataStore read (the key lacks the scope).
The fallback (a community ProfileStore module) is **not needed**.

## Question
Can the wallet and an idempotent receipt ledger live in a session-locked DataStore profile, with
`ProcessReceipt` granting only after a durable save? And does DataStoreService work in Luau Execution?
(BUILD_PLAN §4.3 S15, D14, D26, risk 24.)

**ProfileStore lock.** Every write is an `UpdateAsync` whose transform checks the lock
`{ jobId, session, expires }`:
- A load waits while another session holds a live lock: `lockWaits` (4) tries, `lockWaitSeconds` (4) apart.
- It takes over ("stolen") once the lease has expired (180 s), which covers a crashed server.
- A save that finds a lock it does not own writes nothing and marks the profile `lost`.
- Calls retry with exponential backoff (4 retries, starting at 1 s).
- `step(now)` autosaves every 30 s, which also renews the lease.
- `release()` clears the lock.
- `readOnly()` returns a read-only profile for the D14 fallback.

**ProcessReceipt semantics** (`Receipts.process`):
- **NotProcessedYet** when:
  - the product is unknown;
  - there is no profile, or it is read-only;
  - the lock was lost to another server;
  - the save failed.
- **PurchaseGranted** only once the save that holds the credit has succeeded.
- **Redelivery** of a PurchaseId:
  - already durable: grants without crediting;
  - credited in memory but not yet saved: saves again and does not credit again.

  This makes an ambiguous save (committed, then an error) safe.

## Numbers against the plan's criteria
**Lune** (`tests/unit/economy_wallet.spec.luau` 6 cases, `tests/unit/persistence_receipts.spec.luau` 14 cases, all passing):
- **Two servers.** B is refused while A holds the lock (status `locked`, after 2 × 5 s of waiting). After A releases, B loads A's balance.
- **Crash.** A stops renewing. After 181 s B steals the profile. A's late save is refused (`lost`), and the stored balance stays at A's last durable value.
- **Retries.** Two throttles followed by success loads correctly, after 1 s + 2 s of backoff. Five errors in a row fail the save but keep the lock, and the next save succeeds.
- **Receipts:**
  - not loaded: NotProcessedYet, then granted once the profile loads;
  - triple delivery: credited once;
  - failed save: NotProcessedYet, and the redelivery grants without a second credit;
  - ambiguous save: credited once, with one ledger entry;
  - crash after the save: the next server grants with 0 credits;
  - crash before the save: credited exactly once on the next server;
  - the old server after a steal: NotProcessedYet.
- **Randomised soak.** 2,000 deliveries with 5 % injected faults (errors and commit-then-error), crashes and failovers on 2 % of steps, and redeliveries of recent granted IDs. Every purchase was granted in the end, and the stored wallet equals 1 credit per purchase.

**Engine.** One Luau Execution task on CI place v9 with `--inject`: `tools/cloud/tasks/receipts_probe.luau`, which runs `tests/engine/Receipts.luau`.

## Carry-forward for W1 and W4
- **W4 #11 wiring:**
  - `Persistence/Profiles` is a service around `ProfileStore.new(DataStoreService:GetDataStore("profiles-v1"), { jobId = game.JobId, now = os.time, sleep = task.wait })`.
  - Load on `PlayerAdded` before the first possession.
  - `release()` on `PlayerRemoving`.
  - `BindToClose` releases every profile, in parallel `task.spawn`s.
  - A `Heartbeat` loop calls `profile:step(os.time())`.
  - `MarketplaceService.ProcessReceipt = function(info) return Enum.ProductPurchaseDecision[handler:process(info)] end`.
- **Keep the session lock's wall clock on `os.time()`.** It is shared across servers; `os.clock()` is per process.
- **Add a "release request" through MessagingService.** It lets a player who hops servers not wait out the 180 s lease when the old server is alive but slow to release. The hand-rolled lock is enough without it; ProfileStore does the same.
- **Ledger KEEP = 200** is safe because Roblox never redelivers a receipt after `PurchaseGranted`. Do not lower it below the most a player could buy within one redelivery window.
- **`Economy/Credits` and `Persistence/Profiles` are still W0 stubs.** Spending (`Wallet.debit`) and prices from `prices.json` arrive with W4 #11.
- **CI.** Once the key has the DataStore read scope, add an Open Cloud read of `ci-s15-probe/probe` to the cloud CLI and compare it with the engine's `GetAsync` (the plan's "Open Cloud read matches").

1. Go to create.roblox.com → **Creations** → experience **Spicy Rodent** (Universe 10775476638; not the duplicate "Spicy Rodents").

4. Repeat for "400 Spicy Dollars" at **100** Robux and "1,600 Spicy Dollars" at **400** Robux.
5. Copy the three **Product IDs** from the list and send them to Claude, who wires them into `economy/products.json`.

**C. Open Cloud DataStore read (CI verification):**
1. Go to create.roblox.com → **Open Cloud** → **API Keys**.
2. Open the existing key → **Edit**.
3. Under **Access Permissions**, choose **Add API System** → **universe-datastores** (Standard Data Stores).
4. Choose the experience **Spicy Rodent**. Under operations, tick **Read Entry** (`universe-datastores.objects:read`) and **List Entry Keys**. Leave writes off.
5. **Save Changes**, and tell Claude. Claude re-runs the read; it should return `{ n = 1 }`.

**D. The Studio purchase check** (about 5 minutes, after B and the W4 wiring): Play in Studio → buy the 25 R$ product (Studio test purchases are free) → the wallet shows S$100.00 → Stop → Play again → still S$100.00.
